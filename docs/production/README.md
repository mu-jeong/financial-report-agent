| 항목 | 값 |
| --- | --- |
| 문서 상태 | 기획 초안 |
| 문서 버전 | 0.3.1 |
| 기획 책임자 | 제품 책임자 / 단일 운영자 |
| 기술 검토자 | 지정 필요 |

> **적용 범위:** 현재 저장소에서 개발·검증하는 대상은 PoC/MVP다. 이 디렉터리는 그 코드를 곧바로 운영판으로 승격하기 위한 계약이 아니라, **별도로 진행할 운영판의 기획 초안**이다. 현재 코드는 현황과 재사용 가능성을 확인하는 참고 근거이며, 운영판의 구현 상태로 간주하지 않는다.

Figma는 운영판 기획을 처음 접하는 사람이 전체 구조와 관계를 파악하는 1차 열람 화면이다. 이 디렉터리는 검토 중인 정책·요구사항·미결정 사항을 기록한다. 운영판 저장소가 만들어진 뒤 승인된 계약과 구현 근거는 그 저장소에서 관리한다.

핵심 결론은 다음과 같다.

1. 검색과 답변의 기준 데이터는 계속 로컬 SQLite/FAISS 및 로컬 산출물이다.
2. Supabase는 관측·이슈 수집·배포 이력 관리를 위한 원격 운영 영역의 후보 기술이다. 현재 저장소에는 익명 이슈 접수의 서버/클라이언트 1단계가 구현되어 있고 hosted 배포·권한 검증까지 완료됐다.
3. 원격 장애가 검색, 답변, 로컬 저장을 막아서는 안 된다.
4. 공개 배포 클라이언트에는 secret/service-role/DB 자격증명을 넣지 않는다.
5. 설치 UUID는 익명 상관관계 식별자이며 device credential이 아니다.
6. 프로그램 배포본, 설치별 로컬 실행 상태, 서버 수집 상태, 평가 근거를 한 버전으로 섞지 않고 별도로 식별한다.
7. 공개 사용자 데이터는 모두 `untrusted`로 취급하며 자동으로 평가 기준이나 릴리스 승격 근거가 되지 않는다.

## Figma 1차 열람과 Git 기준 원본

Figma와 Git 문서는 같은 내용을 경쟁적으로 보관하지 않는다. Figma는 관계를 한눈에 이해하고 리뷰하기 위한 시각적 지식베이스이고, Git은 정확한 계약과 변경 이력을 보관한다.

```text
Figma: 전체 지도·흐름·경계·상태·리뷰
  -> Git 기획 문서와 machine-readable contract: 정확한 정의
  -> 코드·테스트·운영 evidence: 구현과 검증
```

| 내용 | 기준 원본 | 비고 |
| --- | --- | --- |
| 제품 목적, 수집 허용 범위, 보존 기간, 승인 정책 | 이 디렉터리의 승인된 기획 문서 | 제품 책임자가 변경 승인 |
| 필드명, 타입, DDL, API 스키마, 버전 계산 | Git의 machine-readable contract와 코드 | 개발자가 테스트와 함께 변경 |
| 실제 실행 동작 | 코드, 마이그레이션, 자동화 테스트 | 문서와 다르면 결함 또는 변경 요청 |
| 사람이 이해하고 리뷰하는 아키텍처·화면·계보·상태 흐름 | Figma | 기획의 1차 열람 화면이며 정확한 스키마의 원본은 아님 |
| 승인 전 중요한 선택과 대안 | `decisions/PROPOSAL-*.md` | 현재는 검토안이며 운영판을 구속하지 않음 |

기획 탐색은 FigJam이나 Figma `Draft`에서 시작할 수 있다. 리뷰 가능한 의미가 정해지면 requirement ID와 acceptance criteria를 Git 문서에 기록하고 Figma Frame ID와 연결한다. Figma의 각 프레임에는 `Doc Ref`, `Requirement IDs`, `Doc Version`, `Git Commit`, `Last Synced`를 표시한다. 관계·상태·정책·수용 기준이 바뀌었다면 Figma만 수정해서 승인된 변경으로 간주하지 않는다.

## 공동 작성 규칙

기획 문장은 `무엇을/왜/어떤 조건에서 성공으로 볼지`를 정의한다. 개발자는 같은 요구사항 아래에 `어떻게 구현하고 무엇으로 검증했는지`를 추가한다.

- 모든 요구사항은 `PROD-*`, `DATA-*`, `VER-*`, `OBS-*`, `IMP-*`, `ENG-*` 식별자를 가진다. 이 식별자는 추적용이며 구현 완료 표시가 아니다.
- 개발 작업·PR·테스트·대시보드는 해당 요구사항 ID를 참조한다.
- `[제품 검토안]`은 기획자가 승인하기 전까지 확정 결정으로 읽지 않는다.
- `[개발 검토 필요]`는 API, DDL, 알고리즘, 성능 측정 방식처럼 기술 책임자가 채울 부분이다.
- 승인 전 변경은 문서 변경 이력에 남긴다. 운영판의 중요한 기술 결정은 운영판 저장소에서 승인될 때 의사결정 기록(ADR)으로 만든다.
- Figma 댓글에서 합의된 내용은 해당 프레임과 Git 문서에 반영한 뒤 해결 처리한다.
- 상태는 `PoC/MVP 구현`, `운영판 기획`, `기획자 입력 필요`, `운영판 구현`, `운영 검증`으로 구분한다.

## 승인 상태

```text
기획 초안
  -> 기획 검토
  -> 기술 검토
  -> 승인
  -> 운영판 구현
  -> 운영 검증
  -> 대체됨
```

- `승인`은 기획 합의이며 구현 완료를 의미하지 않는다.
- `운영판 구현`은 별도 운영판 저장소에 코드가 있다는 뜻이며 운영 검증 완료를 의미하지 않는다.
- `운영 검증`만 운영판 기준 충족으로 간주한다.
- 요구사항 일부가 바뀌면 문서 버전을 올리고 영향받는 구현·테스트·Figma 링크를 다시 검토한다.

## 범위 전제

- 운영자: 배포, Supabase, 이슈 분류, 평가·승격을 관리하는 한 명의 관리자.
- 사용자: 설치 파일을 받아 로컬에서 실행하는 불특정 다수. 운영자 계정과 동일하지 않다.
- 권위 데이터: 로컬 문서, SQLite catalog, FAISS snapshot, 로컬 대화/이슈 산출물.
- 원격 데이터: 익명화된 운영 이벤트, 명시적으로 제출한 이슈, 평가 요약, 릴리스 매니페스트.
- 초기 단계에서는 원격 데이터가 답변 생성이나 검색 결과를 변경하지 않는다.

## 의사결정 기록 사용 기준

의사결정 기록(ADR)은 기존 결정이 바뀔 때만 쓰는 문서는 아니다. 처음 채택하는 중요한 구조적 결정도 기록할 수 있다. 다만 현재는 운영판 구조가 승인되지 않았고 운영판 개발도 별도로 진행할 예정이므로, 이 저장소에서 운영판 ADR을 확정할 필요는 없다.

- 현재 `decisions/PROPOSAL-*.md`는 비교와 검토를 위한 **의사결정 검토안**이다.
- 운영판 착수 시 채택된 검토안만 운영판 저장소의 ADR로 옮긴다.
- 운영판에서 승인된 결정을 나중에 바꾸면 새 ADR이 이전 ADR을 대체하도록 기록한다.
- 현재 PoC/MVP 구현 자체에 장기적으로 유지할 중요한 결정이 있다면 그 결정만 이 저장소의 ADR 대상이 될 수 있다.

## 현재 구현과의 관계

현재 PoC/MVP 저장소에는 로컬 스키마 버전, 검색 정책 해시, 자료 묶음 목록, 빌드·스냅숏 식별자, 게시 세대, 재현 정보, 원격 이슈 제출·회귀 후보 상태 전이와 평가 실행 코드가 있다. 관련 계약 시험은 존재하지만 승인된 기준 질문 파일과 기대 결과는 비어 있다.

Supabase `issue-report-ingest` Edge Function, private issue/rate-limit tables, service-role 전용 원자적 RPC, 엄격한 입력 검증, retry-only SQLite outbox, 최소정보 redaction과 비동기 재시도 클라이언트는 저장소에 구현되어 있으며 hosted 배포·권한 smoke test와 보존 Cron 검증까지 완료됐다. 로컬 `.txt`/`.json` 신고 파일은 새로 만들지 않고 terminal outcome에서 outbox payload를 즉시 제거한다. 다만 일반 관측 이벤트, 운영자 인증 화면, 서버 수집 배포 식별, 승인된 배포 기록, 수동 설치·복구 절차는 구현 또는 운영 검증이 끝나지 않았다. 따라서 **운영판 개선 과정은 완성된 상태가 아니다.**
