# V2 전환 자체 검증 확인서

이 문서는 개인용 Finance LLM 설치가 V1 데이터에서 쓰기 가능한 V2 검색 구조로
정상 전환되었는지 확인하기 위한 한국어 기록 양식입니다. 조직용 승인 절차나 별도의
릴리스 허가 문서가 아니라, 나중에 문제가 생겼을 때 현재 상태와 백업 위치를 빠르게
확인하기 위한 개인용 점검표입니다.

V2 전환의 핵심 원칙은 다음과 같습니다.

- 검증된 V2만 활성화합니다.
- V2가 활성화되면 V1 fallback은 영구적으로 닫습니다.
- V1 원본과 백업은 자동 삭제하지 않습니다.
- 인증 여부와 V1 데이터 삭제 여부를 연결하지 않습니다.

## 적합 판정

다음 조건을 모두 충족하면 V2 전환을 `적합`으로 기록할 수 있습니다.

1. `MIGRATE_V2.bat`이 `[완료]`로 끝났습니다.
2. 활성 검색 구조가 V2 native snapshot입니다.
3. `write_epoch > 0`입니다.
4. `v1_fallback_open=false`입니다.
5. `write_enabled=true`이고 degraded 상태가 아닙니다.
6. 실제 앱에서 질문과 검색이 정상 동작합니다.
7. 앱을 종료하고 다시 실행해도 같은 V2 데이터를 정상적으로 읽습니다.
8. 데이터 업데이트 기능이 필요한 설치라면 신규 또는 변경 문서 반영이 정상 동작합니다.
9. V1 원본과 `.v2m/<실행 ID>/v1/` 백업이 보존되어 있습니다.

하나라도 충족하지 못하면 `보류`로 기록합니다. V1 파일을 삭제해서 문제를 해결하려고
하지 말고, `.v2m/<실행 ID>/failure.json`과 `cutover-journal.json`을 먼저 확인합니다.

## 자동으로 검증되는 항목

`MIGRATE_V2.bat`은 다음 검사를 자동으로 수행합니다.

1. V1 SQLite 데이터베이스와 FAISS/pickle 파일의 안전한 복사본 생성
2. V1 DB·벡터·문서 매핑 수와 원본 PDF SHA-256 확인
3. 라이브 데이터 밖에서 V2 호환 seed 변환
4. 현재 임베딩 모델과 기존 벡터가 같은 공간인지 canary 검사
5. 변환된 seed를 쓰기 가능한 V2로 승격
6. 격리된 V2의 읽기·쓰기 및 GUI 실행 검사
7. 전환 직전 V1 DB·벡터·PDF가 바뀌지 않았는지 재확인
8. V2 활성화 후 라이브 GUI 실행 검사

성공 직후 생성되는 `migration-receipt.json`에는 다음 값이 기록됩니다.

- `kind`: `finance_llm_v2_user_migration_receipt`
- `status`: `migrated`
- `snapshot_id`: 활성화한 V2 snapshot
- `publication_generation`: 전환 직후 publication 세대
- `write_epoch`: `1` 이상
- `v1_fallback_open`: `false`
- `write_enabled`: `true`
- `backup_relative_path`: `v1`
- `canary`: 임베딩 호환성 검사 결과

전환 후 데이터 업데이트를 수행했다면 현재 `publication_generation`과 `write_epoch`은
영수증의 값보다 커질 수 있습니다. 이는 정상이며, 값이 증가했다고 전환 인증이
무효가 되지는 않습니다.

## 직접 확인할 항목

자동 검사와 별도로 다음 항목만 실제 사용 방식으로 확인합니다.

- `RUN_APP.bat`으로 앱이 정상 실행됩니다.
- 기존 문서에 대한 질문과 검색 결과가 정상적으로 표시됩니다.
- 앱을 완전히 종료한 뒤 다시 실행해도 검색이 정상 동작합니다.
- 평소 사용하는 데이터 업데이트 기능이 정상 완료됩니다.
- 업데이트 후 추가하거나 변경한 문서가 검색 결과에 반영됩니다.
- 기존 V1 문서도 빠짐없이 검색할 수 있습니다.

개인적으로 데이터 업데이트 기능을 사용하지 않는다면 관련 항목은 `해당 없음`으로
기록할 수 있습니다.

## V1 데이터 보존 정책

V2 검증 완료는 V1을 더 이상 검색 fallback으로 사용하지 않는다는 뜻입니다. V1 파일을
물리적으로 삭제한다는 뜻은 아닙니다.

| 대상 | 전환 후 상태 | 자동 삭제 |
| --- | --- | --- |
| 라이브 V1 `reports.db` | 원본 그대로 보존 | 안 함 |
| 라이브 V1 `vector_db/` | 원본 그대로 보존 | 안 함 |
| 라이브 `downloaded/` PDF | 원본 그대로 보존 | 안 함 |
| `.v2m/<실행 ID>/v1/` | 전환 시점 백업으로 보존 | 안 함 |
| `retrieval/compat/v1/<bundle ID>/` | 봉인된 호환성 묶음으로 보존 | 안 함 |
| V2 `retrieval/` | 현재 활성 검색 구조 | 해당 없음 |

V1 fallback은 `write_epoch > 0`이 된 뒤 다시 열리지 않습니다. 따라서 V1 데이터가
남아 있어도 정상 실행 중인 앱이 이를 검색 대상으로 자동 선택하지 않습니다.

디스크 공간을 정리하려면 충분한 사용 기간과 별도 백업을 확보한 뒤 사용자가 직접
보존 범위를 결정합니다. V1 삭제는 이 확인서의 합격 조건도, 자동 후속 단계도 아닙니다.

## 최종 해석

- `적합`: V2가 쓰기 가능한 상태로 활성화되었고 실제 사용 확인을 통과했습니다.
- `보류`: 자동 검사 또는 직접 확인 중 하나 이상이 실패했거나 결과를 확인하지 못했습니다.
- V1 원본과 백업이 남아 있는 것은 정상입니다.
- V1 fallback이 닫혀 있는 것도 정상입니다.
- 별도로 V1을 삭제하지 않아도 V2 전환은 완료된 상태입니다.

상세한 전환 동작은 [일반 사용자용 V2 마이그레이션](V2_MIGRATION_USER.md), 내부 구조와
복구 원리는 [V2 마이그레이션과 검색 아키텍처](V2_MIGRATION.md)를 참고하세요.
